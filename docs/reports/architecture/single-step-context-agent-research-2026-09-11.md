# Single-Step Context Agent Architecture Research

**Date:** 2026-09-11  
**Scope:** Current on-disk repository, approved/local governance, and primary sources. No tests were run and no implementation/configuration/Git state was changed.

## Executive conclusion

The proposal has a sound core: authenticated standalone conversations; PostgreSQL as canonical application state; Chroma retained as a read-only travel-knowledge projection; read-only Memory and Travel Knowledge capabilities; bounded execution; deterministic context policy/arbitration; and asynchronous memory formation through a transactional outbox. It should not, however, be implemented as seven independently deployed or model-driven agent services. At this maturity, use one application service with typed, mostly pure internal modules and two read ports.

“Single-step” and “one tool round” need normative definitions. If a model first chooses tools, the application executes them, and a model then generates the answer, that is two model calls and one tool-execution round. If MemoryReadTool and TravelKnowledgeTool are exposed as separate calls while only one call is permitted, “both” is impossible unless the round allows a bounded set of parallel read requests or a composite context-read operation. Prefer an application-computed `ContextPlan` that executes zero, one, or both read ports once, followed by exactly one response-generation call; introduce provider-native model tool selection only after deterministic routing proves inadequate.

The proposal is not approved implementation scope. The approved clean-break design explicitly defers adaptive selection, Dialogue reference resolution, ActionRouter, ContextPlanner, ContextArbiter, V2 Memory Read/Use, and agent execution (`docs/specs/2026-09-10-authenticated-chat-postgresql-clean-break-design.md:24-28,152-161`). The broader unified memory design is **In Review**, not approved (`docs/specs/2026-09-10-unified-multi-conversation-agent-memory-architecture.md:1-12,750-754`). A new Level-3 spec, architecture approval, ADRs, and approved implementation plan are therefore required.

## Confirmed repository facts

1. **Authenticated, owner-scoped standalone conversations are real.** The route requires a principal and calls `handle_turn` (`backend/app/api/chat.py:54-84`); ADR 0021 fixes owner identity to the authenticated principal, auto-create semantics, and non-enumerating cross-owner behavior (`docs/adr/0021-standalone-conversation-ownership-and-auto-create.md:47-70`). Repository transactions bind and verify `app.tenant` before work (`backend/conversations/postgres_repository.py:68-79`).
2. **The chat turn uses the accepted two-phase persistence contract.** First-turn creation atomically writes conversation, complete user row, pending assistant row, and optional outbox row (`backend/conversations/postgres_repository.py:209-319`). Existing turns allocate adjacent user/assistant sequences under a parent-row `FOR UPDATE` lock and insert the optional outbox event in the same transaction (`backend/conversations/postgres_repository.py:608-731`). Completion/failure is a guarded pending-row transition; failure cancels that turn’s pending outbox event in the same transaction (`backend/conversations/postgres_repository.py:733-863`).
3. **Online behavior is fixed RAG, not an agent/tool loop.** `ConversationOrchestrator` always calls `RAGService.generate_answer(message, top_k=4)` after phase one and returns `memory=None` (`backend/orchestration/conversation_orchestrator.py:153-229,263-264`). `RAGService` always embeds/retrieves/assembles before generation (`backend/rag/generation/rag_service.py:55-100`); retrieval uses BGE-M3 and a read-only Chroma collection (`backend/rag/retrieval/service.py:12-56`). No proposed `DialogueStateResolver`, `ActionRouter`, `ContextPlanner`, `ContextPolicy`, `ContextArbiter`, `ResponseGenerator`, `ConversationWorkingState`, `MemoryReadTool`, `TravelKnowledgeTool`, or provider tool-call handling exists in bounded `backend/**/*.py` search.
4. **Current generation has no conversation continuity.** Only the current user message and retrieved travel chunks are sent to generation (`backend/orchestration/conversation_orchestrator.py:263-264`; `backend/rag/generation/llm.py:73-112`). The context assembler concatenates retrieved document text directly and considers evidence insufficient only when retrieval returns zero rows; it has no score threshold (`backend/rag/generation/context.py:12-68`).
5. **The provider boundary is endpoint-configurable but SDK-specific.** Generation imports the OpenAI SDK and uses `chat.completions.create` (`backend/rag/generation/llm.py:9,73-112`), while model and base URL are deployment configuration (`backend/app/config.py:27-43`). This supports OpenAI-compatible endpoints, not provider-neutral tool semantics. No Anthropic dependency was found, so Anthropic-specific design is not warranted now.
6. **The memory write capability is narrow and default-off.** Both memory gates default false (`backend/app/config.py:80-86`), and the runtime only passes the shadow-extraction gate into the orchestrator (`backend/app/runtime_container.py:219-235`). The registry contains one key, `travel.preference.hotel_atmosphere`, with only user and conversation scopes (`backend/memory/write_pipeline/registry.py:23-64`); domain precedence is only `explicit_save > explicit_statement > repeated_inference` (`backend/memory/write_pipeline/models.py:28-41`). There is no implemented semantic/episodic/working/procedural family taxonomy or mounted Memory Read path.
7. **Background extraction is shadow-only.** The recorder deliberately replaces the resolver’s operation with `NOOP`, persists evidence/decision with a semantic idempotency key, and creates no active version (`backend/memory/write_pipeline/background_recorder.py:274-339`). Therefore a future `MemoryReadTool` has no currently approved active inferred-memory corpus to read.
8. **The outbox is a useful but incomplete worker substrate.** Batch claims use `FOR UPDATE SKIP LOCKED` and serialize one event per conversation (`backend/memory/write_pipeline/outbox.py:429-518`). The worker revalidates conversation/deletion state, scans secrets before model exposure, revalidates its lease, and supplies a transactional fence to the memory UoW (`backend/memory/write_pipeline/worker.py:228-332,416-500`). However `mark_failed` updates without checking status or `lease_owner` (`backend/memory/write_pipeline/outbox.py:552-596`), and the in-transaction lease fence checks status/owner but not `lease_until` (`backend/conversations/postgres_repository.py:1038-1061`).
9. **Extraction range semantics remain underspecified.** New outbox payloads contain conversation/deletion metadata but no stable end cursor (`backend/orchestration/conversation_orchestrator.py:93-145`; `backend/conversations/postgres_repository.py:673-692`). The worker may reload up to 100 messages from the start when `after_sequence` is absent (`backend/memory/write_pipeline/worker.py:277-294,536-582`). This risks repeated extraction and omission once a conversation exceeds the fixed window.
10. **Architecture documentation has drift.** It depicts an online call to `BackgroundMemoryRecorder` after assistant append (`ARCHITECTURE.md:46-75`; `docs/architecture/current-state.md:70-100`), but current orchestration only inserts an outbox intent during phase one and never calls the recorder (`backend/orchestration/conversation_orchestrator.py:93-168`). The old target-state still makes Trip Workspace primary (`docs/architecture/target-state.md:27-37`), conflicting with accepted clean-break decisions. Treat source plus accepted ADRs as authoritative.

## Primary-source findings

- PostgreSQL transactions provide all-or-nothing visibility: intermediate states are not visible and commit makes updates visible together. This supports message-plus-outbox atomicity, but not exactly-once external model effects: <https://www.postgresql.org/docs/current/tutorial-transactions.html>.
- `SELECT ... FOR UPDATE` blocks conflicting writers/lockers of the same row until transaction end; deadlocks require consistent lock order and whole-transaction retry handling: <https://www.postgresql.org/docs/current/explicit-locking.html>. PostgreSQL’s default Read Committed level gives each statement a new snapshot and re-evaluates predicates after waiting; stronger levels can raise serialization failures requiring full transaction retry: <https://www.postgresql.org/docs/current/transaction-iso.html>.
- `SKIP LOCKED` intentionally yields an inconsistent view and is suitable for queue-like consumers, not general reads. Thus queue lag, fairness, retries, and reconciliation remain application obligations: <https://www.postgresql.org/docs/current/sql-select.html>.
- RLS defaults to deny when enabled with no applicable policy, but table owners normally bypass it and superusers/`BYPASSRLS` always do; `FORCE ROW LEVEL SECURITY` plus a non-owner, non-bypass runtime role is the correct defense-in-depth shape: <https://www.postgresql.org/docs/current/ddl-rowsecurity.html>.
- OWASP says RAG documents, files, websites, and stored memory can carry indirect prompt injection; separate untrusted content from instructions, constrain capabilities, apply least privilege, validate structured output, and require approval for privileged actions: <https://genai.owasp.org/llmrisk/llm01-prompt-injection/> and <https://genai.owasp.org/llmrisk/llm062025-excessive-agency/>. It also recommends minimizing connected data, sanitizing sensitive data, access controls, retention rules, and user transparency: <https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/>.
- NIST organizes AI risk work as Govern, Map, Measure, Manage and the GenAI Profile calls for context-specific TEVV/adversarial testing, monitoring, accountable human roles, privacy/provenance review, incident processes, and third-party dependency assessment: <https://doi.org/10.6028/NIST.AI.100-1>, <https://airc.nist.gov/airmf-resources/playbook/>, <https://doi.org/10.6028/NIST.AI.600-1>.
- Because the current code uses OpenAI’s SDK, its official tool guidance is relevant only as adapter evidence: strict schemas, disabled parallel calls, forced/required/none tool choice, application-side execution, and a follow-up output linked by call ID can enforce one bounded round. These are provider-specific fields and must not enter domain contracts: <https://developers.openai.com/api/docs/guides/function-calling>.

## Reasonable inferences

1. The safest “agent” here is a bounded context coordinator, not an autonomous loop: all proposed capabilities are reads, and deterministic application orchestration is easier to authorize, observe, and evaluate than model-selected control flow.
2. Seven named components are useful as responsibilities but overdesigned as seven classes/services now. `DialogueStateResolver` and `ActionRouter` can initially be one pure `TurnInterpreter`; `ContextPlanner`, `ContextPolicy`, and `ContextArbiter` can be one `ContextCoordinator` with separately tested pure policy functions. `ResponseGenerator` should remain a port/adaptor boundary.
3. `ConversationWorkingState` is internally inconsistent unless its authority is explicit. If ephemeral, call it `TurnContext` and derive it per request. If durable, it needs PostgreSQL ownership, source-message cursor/range, schema/version, optimistic-concurrency rule, freshness/staleness, rebuild/delete behavior, and must not duplicate durable semantic memory.
4. Read-only tools reduce excessive-agency risk but do not solve confidentiality or prompt injection: Memory results are personal data and both Memory and travel chunks are untrusted prompt data. Neither may supply executable instructions, authorization decisions, SQL, or lifecycle mutations.
5. “Memory types/scopes/precedence” cannot be one global ordering. Eligibility and precedence need dimensions for source authority, current-turn override, scope, lifecycle, sensitivity, temporal validity, conflict state, and relevance. Travel knowledge remains cited evidence; memory is personalization context, not a factual citation.

## Missing contracts and invariants

Define versioned contracts before code: `TurnInput`, `DialogueState`, `ActionRoute`, `ContextPlan`, `ReadRequest`, `ReadResult`, `ContextCandidate`, `ArbitrationDecision`, `ContextEnvelope`, and `TurnResult`. Closed reason/status enums must distinguish `not_needed`, `selected`, `empty`, `filtered`, `timed_out`, `unavailable`, and `invalid`.

Required invariants: principal identity only from authentication; owner/scope/lifecycle/sensitivity filtering occurs inside each read port; both tools are side-effect-free; model output never authorizes access or mutation; current request overrides soft memory; unresolved/conflicting/deleted/shadow memory is ineligible; travel claims require citations; memory is never represented as a citation; raw evidence is excluded by default; token/item/time budgets are deterministic; the response model receives one typed envelope; one generation call follows at most one bounded read round; no fallback silently changes owner, scope, provider, or store.

Define “one round” as: one `ContextPlan`, containing at most one request per read capability, executed concurrently or sequentially under a shared deadline, with no tool result allowed to trigger another read in the same turn. If model-native planning is later used, permit one planning response, execute its validated bounded set once, then force no tools on generation.

Failure contracts must cover: resolver invalid/timeout; each tool empty/timeout/unavailable; both tools unavailable; Chroma missing/corrupt; stale working state; context budget overflow; generation timeout; generation success plus assistant-write failure; delete during read/generation; outbox lease expiry during extraction; poison event/dead letter; worker crash after semantic commit; duplicate client submission; and PostgreSQL serialization/deadlock retry exhaustion. Knowledge failure should abstain from unsupported factual claims; Memory failure should degrade to no-personalization and be visible in controlled metadata.

Privacy contracts must identify purposes, fields sent to each provider, retention/training terms, user disclosure/control, sensitivity exclusions, deletion propagation to summaries/indexes/caches, and account deletion. Current local bearer auth and local PostgreSQL are not production identity/retention guarantees; the repository itself marks public production blocked (`SECURITY.md:128-152,212-224`).

Observability must record content-free IDs and versions: request/turn/conversation, interpreter/route/plan reason codes, tool attempts/status/latency/count, selected IDs and exclusion reasons, arbitration conflicts, context token budget, prompt/schema/model/provider adapter versions, generation latency/failure class, assistant persistence state, outbox age/retry/dead-letter/lease loss, and state freshness. Do not log prompts, raw messages, memory values, retrieved chunks, tool arguments containing user data, or provider output.

Evaluation needs component and end-to-end datasets for reference resolution, route choice, plan exact match, read eligibility/ranking/abstention, scope/precedence/conflict/temporal correctness, RAG relevance and citation support, arbitration, response use/over-personalization, prompt injection, privacy leakage, cross-owner denial, deletion, concurrent turns, one-round adherence, degraded paths, latency, tokens, and cost. Zero-tolerance gates: cross-owner selection, deleted/ineligible memory use, prohibited-secret model exposure, instruction execution from retrieved data, uncited supported-travel claims where citation is required, and non-idempotent durable effect. “Not measured” must not pass.

## Recommended staged target architecture

**Stage 0 — approve contracts and baseline.** Reconcile architecture docs; write the Level-3 spec/ADRs/plan; define the round, state authority, error matrix, privacy data flow, metrics, and evaluation fixtures. Keep memory gates off.

**Stage 1 — bounded conversation understanding.** Load an owner-scoped transcript tail plus any versioned durable summary; implement a rule-first `TurnInterpreter` for references and route (`answer_without_external_context`, `travel_knowledge`, `memory`, `both`, `clarify`). No model tool call and no memory use yet. Evaluate ambiguity and fallback.

**Stage 2 — `TravelKnowledgeReader`.** Wrap existing `KnowledgeRetriever` behind a provider-neutral read port with strict request/result schemas, deadlines, score/quality policy, citation provenance, injection-safe formatting, and `empty` versus `unavailable`. Preserve Chroma as a rebuildable global projection.

**Stage 3 — `MemoryReader` shadow integration.** Implement exact structured PostgreSQL reads first, enforcing owner, active lifecycle, scope, sensitivity, source validity, conflict, temporal and budget filters in storage/application code. Return typed influence labels and controlled IDs, never raw evidence. Run selection in shadow and do not send it to generation until privacy and retrieval gates pass. Do not pretend the current shadow-only corpus is answer-eligible.

**Stage 4 — one context coordinator.** Add `ContextCoordinator.plan_and_assemble`, containing pure policy/arbitration functions. It executes zero/one/both readers once and produces a typed `ContextEnvelope`; `ResponseGenerator` consumes only that envelope. Keep one final generation call. Feature-gate Memory read separately from Memory prompt use for rollback.

**Stage 5 — durable working state and memory formation.** Add `ConversationWorkingState` only as a versioned, evidence-ranged PostgreSQL projection after summary/state evaluation passes. Repair outbox cursor/end-range, lease-expiry fencing, lease-owner-guarded failure transitions, poison/recovery/runbooks, and worker metrics before enabling formation. Enable active memory one type/key/scope vertical slice at a time; semantic first, then working summaries, then episodic. Defer procedural memory to a separate governed publication path.

**Stage 6 — optional provider-native tool planning.** Only if measured queries require it, add a provider-neutral `ToolPlanner` interface and adapter-specific OpenAI-compatible implementation. Enforce strict schemas, no writes, no parallel duplication, shared deadline, one execution round, and forced no-tools generation. Do not add Anthropic-specific architecture unless an approved provider decision selects it.

The minimal dependency direction should be `HTTP -> ContextAgent application service -> TurnInterpreter + ContextCoordinator -> Conversation/Memory/Knowledge read ports + ResponseGenerator -> PostgreSQL/Chroma/model adapters`. Background flow remains `message+intent transaction -> outbox worker -> formation/policy/UoW`; it does not join the synchronous read round.

## Unresolved questions and evidence limitations

- No authoritative proposal document beyond the owner’s stated component list was supplied, so exact semantics of “single-step,” “one tool round,” `ConversationWorkingState`, memory families, and precedence remain unresolved.
- No live PostgreSQL/Chroma/provider execution, tests, migrations, load tests, or evaluation runs were permitted. Concurrency and failure conclusions are source/document analysis, not runtime measurements.
- CodeGraph plus direct source reads were used against the dirty on-disk tree; findings describe that tree, not necessarily `HEAD`. Negative symbol/tool-loop claims are bounded to repository `backend/**/*.py` and governance search performed on 2026-09-11.
- PostgreSQL documents transactions, locks, isolation, RLS, and `SKIP LOCKED`; it does not make the application outbox or external model call exactly once. Those guarantees remain application-level and require tests/reconciliation.
- Current governance conflicts remain: the unified memory architecture is in review, old target-state documentation is stale, and accepted ADR 0020 removed public memory controls while ADR 0017 remains historical risk input. Owner decisions are needed on reintroducing chat-based inspect/correct/forget and on production provider/privacy terms.
